# Formal verification of flare

This report describes a Lean 4 model of the flare networking library at commit
59bda50, the theorems proved about it, and the bugs the proofs turned up. It is
generated by `formal/scripts/stitch_report.py` from the per-layer sections in
`formal/report/`; edit those, then rerun the script.

## 1. Summary

The model covers flare from the byte codecs up to the multi-worker scheduler.
L1 is the pure encodings (byte order, socket addresses, UTF-8, varints, HPACK
integers and Huffman, civil time). L2 is the OS-facing machines (sockets, write
loops, the reactor, the timer wheel, io_uring rings, UDP batching, DNS, UNIX
listeners). L3 is the protocols: HTTP/1.1 framing on the server and the client,
WebSocket frames and handshakes, HTTP/2 and HPACK with a refinement proof
against the RFC 9113 stream states, and QUIC (including its idle and
closing timers), QPACK and HTTP/3. L4 is the
application layer (the HTTP/1.1 connection state machine, routers, middleware,
the client's URL parser, redirects and pool). L5 is the concurrency layer
(watchdog, AsyncRT cell, thread handles, scheduler lifecycle, and how long
shutdown takes). On top sits a
model of one reactor worker's event loop that takes any per-connection model,
instantiated with the L4 connection state machine and then lifted to several
workers sharing one fd table. Separately, every security claim in
`docs/security.md` and `docs/threat-model.md`, and the protocol and server
claims in `docs/features.md`, was checked against the code.

For each component the report gives a specification written from the RFC or
from flare's own documentation, an implementation model transliterated from
the Mojo source, and theorems relating the two: refinement, round trips,
invariants over every reachable state, progress, absence of overflow, and
independence from how the input is split into reads. Where a proof failed
because the code is wrong, the finding has three parts: a Lean counterexample
on a concrete input, a Lean proof that a minimal fix meets the specification,
and a Mojo program that reproduces the bug against the real library and passes
once the fix is applied. Each fix was applied temporarily (in the Linux
container's copy of the repo for Linux-only repros), the repro was rerun and
printed `OK:`, and the file was reverted, so `flare/` is unchanged on this
branch. The findings also include gaps between flare's security documentation
and its code (section 6).

Six findings are rated high:

- ENC-03: an 11-byte unauthenticated gRPC health request aborts the server in
  a checked build (an out-of-bounds read in an unchecked one), because
  `ProtoReader`'s length check overflows.
- NET-01: `UdpSocket.recv_from` reports the wrong sender for every IPv6 peer
  and reads 8 bytes past its buffer.
- H2-01: the HTTP/2 connection-level receive window is never enforced, so a
  client can make the server buffer request bodies past it.
- QPACK-01: when the QPACK dynamic table is enabled (it is off by default), a
  field section with Required Insert Count 0 can still read entries from it.
- APP-48: a WebSocket upgrade on a TLS connection is answered in cleartext.
- CONC-03: `Scheduler.drain` can free the stop flag while a detached worker
  still reads it.

The full list with severities is the index at the start of section 5.

The trust base is the Lean 4.33 kernel and core library (no Mathlib), the three
standard axioms `propext`, `Quot.sound` and `Classical.choice`, and, inside
`Flare/Bugs/` only, the compiler-backed `native_decide` for evaluating concrete
counterexamples. `formal-check` fails on any `sorry`, `admit` or `axiom`, on
`native_decide` outside `Flare/Bugs/`, and on any audited theorem whose axioms
go beyond that list. The kernel, libc, OpenSSL and the Mojo runtime are not
modelled. What the proofs need from them is stated as explicit hypotheses
(`Flare/Core/Assumptions.lean` and per-layer `Prop`s such as
`Flare.L2.Udp.RecvfromFills`), so every theorem that depends on one names it.

The models are transliterations, and a transliteration can drift from the code
it copies. Implementation models carry a `mirrors flare/<file>:<lines>
@59bda50` comment naming the Mojo code they copy (proof-only and spec files
have none), the repros check each finding against the real library, and
section 7 lists what was left out.

## 2. Method

### Semantics

Pure codecs (parsers, encoders, predicates) are total Lean functions. Stateful
components are small-step labelled transition systems over the vocabulary in
`Flare/Core/LTS.lean`:

```lean
structure LTS (S : Type) (L : Type) where
  init : S → Prop
  step : S → L → S → Prop

def Reachable (s : S) : Prop := ∃ s₀ ls, M.init s₀ ∧ M.Run s₀ ls s

structure Inductive (P : S → Prop) : Prop where
  init : ∀ s, M.init s → P s
  step : ∀ s l s', P s → M.step s l s' → P s'

structure Simulates (impl : LTS S₁ L₁) (spec : LTS S₂ L₂)
    (abs : S₁ → S₂) (lab : L₁ → L₂) : Prop where
  init : ∀ s, impl.init s → spec.init (abs s)
  step : ∀ s l s', impl.step s l s' → spec.step (abs s) (lab l) (abs s')
```

Safety properties are proved as inductive invariants (`Inductive.reachable`
turns one into a statement about every reachable state). Refinement is forward
simulation (`Simulates.run` maps every implementation trace to a specification
trace). Most models also have an executable step function, lifted with
`LTS.ofFn`, so the same definition can be evaluated on concrete traces and
reasoned about in general. Incremental parsers are checked for
`ChunkingIndependent`: feeding `a ++ b` gives the same result as feeding `a` and
then `b`, so the verdict cannot depend on TCP segmentation.

The concurrency models (L5) are interleaving semantics over a shared heap:
threads are program counters, each atomic load, store, compare-and-swap or free
is one step, and the scheduler is an unconstrained choice with no fairness
assumption. The one exception is the timed teardown model
(`Flare.L5.Timed`), which runs on a millisecond clock and states its
scheduling and timing bounds (a wait returns within its cap, a runnable
thread runs within σ) as hypotheses. The worker-loop machine (`Flare/Machine.lean`) lets the kernel put
any live token in a poll batch, so it assumes nothing about readiness.

### Specification and implementation

Each component pairs a `spec`, written from the RFC (RFC 9112, 9110, 9113,
7541, 6455, 3629, 9000, 9002, 9114, 9204, 8305 and others) or from flare's
docstrings, with an `impl` that keeps the Mojo control flow, limits and
fixed-width arithmetic: Mojo `Int` is `Int64` with wrapping wherever overflow
can matter, ring counters wrap as `UInt32`, and sizes keep their caps. Every
implementation definition carries a fidelity comment naming its source:

```lean
/-- mirrors flare/http2/state.mojo:1005-1333 @59bda50 -/
```

The traceability tables in section 4 list each definition against its Mojo
lines and theorems.

### Findings and repros

A finding is filed only when the Lean counterexample exists and the Mojo
repro, `formal/repro/<ID>_<slug>.mojo`, has been observed to fail against the
real library. Each repro prints `BUG REPRODUCED:` and exits non-zero while the
bug is present, prints `OK:` and exits 0 once it is fixed, and prints
`inconclusive:` and exits non-zero if it cannot set up the scenario, so a broken
setup never passes. Repros were run several times each to check they are
deterministic; those that depend on socket buffer sizes pin `SO_SNDBUF` and
`SO_RCVBUF` and check their precondition before counting an attempt. Repros
marked `# PLATFORM: linux` (io_uring, Linux-only socket behaviour) run in a
Docker container through `formal/repro/linux.sh`. Suspicions that a proof
settled the other way are listed in section 5 under refuted suspicions.
