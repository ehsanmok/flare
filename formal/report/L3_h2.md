# L3 protocol: HTTP/2 and HPACK

This report covers flare's HTTP/2 stack: the frame codec and the server's frame pre-check, the HPACK dynamic table, encoder/decoder table synchronisation and the header-block decoder with its memory budget, request header validation, and the connection state machine. The state machine is `Connection.handle_frame` (`flare/http2/state.mojo:1005-1547`) together with the server driver loop (`flare/http2/server.mojo:398-438`), the client driver loop (`flare/http2/client.mojo:400-512`) and the local actions that change stream or window state. Together they cover stream states, connection and stream flow-control windows, SETTINGS (including MAX_CONCURRENT_STREAMS), GOAWAY, the first frame after the preface, refused-stream bookkeeping, content-length accounting, client-side late frames, and the client's streaming-body mode.

On top of the per-clause theorems there are three whole-connection results:
- a refinement proof against an RFC 9113 §5.1 stream-state LTS, with every departure of the shipped code classified as a reported issue;
- the connection composed with the stateful HPACK decoder, running on flare's real L1 integer and Huffman codecs;
- flow-control and ordering theorems for the client's streaming-body mode.

Each model is a transliteration of the Mojo code at commit 59bda50. Every implementation definition carries a `mirrors flare/<file>:<lines> @59bda50` comment. Specifications are written separately, from RFC 9113, RFC 7541 and RFC 9110. The aggregate module is `Flare/L3_Protocol/H2.lean`, and `Flare/Audit/H2.lean` prints the axioms of 134 headline theorems.

Build and audit status:
- Every module builds on its own with `lake build`. The slowest are `H2/ConnWindow` (about 17 s) and `H2/RefineShipped` (about 13 s); every other module, including the Bugs files, elaborates in under 8 s. There is no `maxHeartbeats` option anywhere.
- There are no `sorry`, `admit` or `axiom` declarations, and no `bv_decide` (it would add `Lean.ofReduceBool`).
- Outside `Flare/Bugs/`, every audited theorem depends only on `propext`, `Quot.sound` and `Classical.choice`.
- `native_decide` appears only in `Flare/Bugs/H2_*.lean` and `HPACK_*.lean`, where it evaluates concrete traces. Every `fixed` theorem is a general proof without `native_decide`.
- The files contain 664 theorems: 518 in the model modules and 146 in the Bugs files.

### Connection state machine and flow control

Files: `H2/Conn.lean` (the model), `H2/ConnSpec.lean` (the RFC requirements and per-clause theorems), `H2/ConnWindow.lean` (the window invariant), and `H2/ConnFlow.lean` (trace-level flow control).

**Model.**
- `handle fx dec c f` transliterates `handle_frame` branch by branch. The DATA, HEADERS and RST_STREAM branches are split into the helpers `dataBody`, `dataAccept`, `dataFinish`, `dataCredit`, `headersPre`, `headersRefuse`, `headersOpen` and `rstFlood`, each with its own line range.
- `_commit_header_block`, the stream table with pruning, `_declared_content_length`, `_active_stream_count` and `release_request_credit` are separate definitions.
- `driveFrame` is the server loop: nothing is applied after a GOAWAY is queued, and over-long frames are refused.
- `driveClient` is the client loop (`client.mojo:400-512`). An over-long frame raises (H2-18), and a PUSH_PROMISE is answered with RST_STREAM before it reaches `handle_frame` (H2-17).
- `step` adds the local actions: `emit_response`, `queue_stream_data`, request-credit release, and the client's `send_request`, `take_response`, END_STREAM (`send_data` / `_emit_body_span`), `enable_response_streaming` and `drain_body`.
- `Stream` carries `defer_body_credit`, `pending_body_credit` and the buffered body octets. `Conn` carries three ghosts: `peerSettingsSeen` (§3.4), `maxLocalSid` (the client's highest opened id) and `decLog` (every header block handed to the HPACK decoder).
- `run` folds `step` over a list of events. `lts fx init` is the LTS whose labels are (decoder oracle, event).
- `Res = Except String …` models a Mojo `raise`.
- `Fix` has one flag per issue. Each fix is a guarded extra branch, so `Fix.none` is exactly the shipped code.

**Spec.**
- `IsConnError o code` (§5.4.1) means the reply is exactly one GOAWAY carrying `code`.
- `ConnWindowOK tr` (§6.9.1) is a monitor on the input/reply trace. It tracks the connection window the peer was actually granted, from the WINDOW_UPDATE(0) frames flare emitted, and fails if a DATA frame exceeds that window without drawing a GOAWAY.
- `peerW` is the peer's view of the connection window after a trace.

### HPACK composed with the connection

Files: `H2/HpackPeer.lean`, `H2/HpackCodec.lean`, `H2/ConnSeq.lean` and `H2/ConnHpack.lean`.

**Model.**

### RFC 9113 §5.1 stream-state refinement

Files: `H2/StreamSpec.lean` (the spec), `H2/RefineAbs.lean`, `RefineData.lean`, `RefineHdr.lean`, `RefineFrame.lean`, `RefineLocal.lean` and `RefineRun.lean` (the simulation), `H2/RefineShipped.lean` (the shipped code), and `Bugs/H2_Refine.lean` (the departure witnesses).

**Spec.** `StreamSpec.lts client` is written from RFC 9113 §5.1 (Figure 2) and nothing else.
- Its state maps each stream id to one of idle, reserved (local or remote), open, half-closed (local or remote), or closed. `none` means the connection has ended.
- Inbound labels carry the frame kind and the verdict: accept, stream error, or connection error with its code. A header block spanning several frames counts as one HEADERS.
- `recvOK` is the §5.1 rule per state. Frames forbidden in a state draw the error class §5.1 prescribes. A stream error is never allowed on an idle stream. WINDOW_UPDATE, RST_STREAM and PRIORITY on a closed stream must be ignored. Connection errors for malformed frames (§4.2), HPACK state loss (§4.3) and resource protection (§10.5) are allowed everywhere.
- Send labels follow `sendPost`: nothing but PRIORITY may be sent on a closed stream, and on half-closed (local) only WINDOW_UPDATE, PRIORITY and RST_STREAM.

**Simulation.** `abs c` maps a connection to its spec state, and `Inv c` (9 fields) is the simulation invariant. `F` is the model with the fixes that bear on §5.1: H2-02, 03, 04, 06, 08 and 11 to 20. H2-01, 05, 07 and 09 concern other sections and stay off.

Scope of the refinement:
- Local actions must respect `LocalOK`, which encodes how flare's callers use the API: for example, `send_request` uses a fresh odd id, and the server only responds on half-closed (remote) streams. H2-12 and H2-13 are exactly the cases where flare's own client code breaks the spec's send rules.
- After a GOAWAY the spec state is `none`, so frames after it are out of scope. The server applies nothing after a GOAWAY, and the client's handler emits nothing more.
- The spec over-approximates in two places. Ignoring DATA on a closed stream is allowed, because it is required after our own RST_STREAM and the spec does not track who closed the stream. A connection error on a late WINDOW_UPDATE or RST_STREAM is never allowed, because the spec has no clock.
- H2-08 is a §3.4 rule, not a §5.1 one. Its departure is shown under the labelling `flab`, which classifies a first frame other than SETTINGS as `other`; `fixed_frame` also proves the §3.4 requirement (`FReq`) directly.

### Client streaming-body mode

File: `H2/Streaming.lean`.

**Model.** `enable_response_streaming` (`client.mojo:1189-1197`) sets `defer_body_credit`. From then on, the body octets of each DATA frame are credited back to the server not when the frame arrives (`state.mojo:1450-1455`) but when the application takes them with `drain_body` (`client.mojo:1160-1187`), which also hands over the buffered octets. The model (`Ev.stream`, `Ev.drain`, `Stream.pendingCredit`, `Stream.buf`) matches the Mojo line by line. The theorems hold for every fix setting, including the shipped code.

| Lean name | Statement | Status |
|---|---|---|
| `step_rel` | Each step keeps every stream's `recvW`, `pendingCredit` and buffer, or creates the stream fresh. Only a DATA frame on stream `k`, or `drain k`, changes stream `k`. A buffer is kept, emptied, or extended by the frame's own payload. `drained` output for `k` is exactly the old buffer of `k`, which is then empty. | proved |
| `ti_step`, `ti_run`, `pending_le` | Per stream, `recvW + pendingCredit ≤ initial window` and `pendingCredit ≤ initial window`, in every reachable state. flare never credits a stream beyond the window it advertised, and the credit held back for undrained octets stays within one initial window. | proved |
| `data_credit` | An accepted DATA frame leaves `recvW + pendingCredit` where it was before the frame was debited. It holds back exactly the deferred body octets (all of them when streaming, none otherwise), and the only stream WINDOW_UPDATE it sends carries the rest of the frame. | proved |
| `drain_credit` | `drain_body` hands over the buffer and credits back exactly the held credit. It sends that credit as a WINDOW_UPDATE while the stream can still receive DATA. | proved |
| `fifo_run` | What `drain_body` handed over on a stream, followed by what is still buffered, is the concatenation of a subsequence of the initial buffer and the DATA payloads received on that stream, in arrival order. Octets are never reordered, duplicated or invented; whole payloads are dropped only when the stream is reset or forgotten. | proved |

No issue was found in this mode.

### Assumptions and limitations

- Frames are abstract records (`Fr`): type, flags, stream id, payload length, and the payload fields the code reads. The byte codec is `Frame.lean`.
- A DATA frame's stripped body is taken to be its `frag` field (a content ghost) for the streaming buffer. Its length, which drives all window arithmetic, is computed from the declared length and padding exactly as in the code.
- Request bodies on the server are represented only by their length. Header lists are represented by their §6.5.2 size where the code only measures them.
- At `state.mojo:826-838`, Mojo stops summing the header-list size at the cap, while the model sums the whole list. The stream is closed in both cases.
- Mojo `Int` is modelled as unbounded `Int`/`Nat`. `win_reachable` shows the send windows stay inside 2^31-1, so they cannot wrap. The one place the code does wrap, `_declared_content_length`, is modelled in `Int64`.
- In the per-clause theorems the HPACK outcome is an oracle `dec`, so they hold for any decoder. `ConnHpack` composes the connection with the real stateful decoder.
- The refinement's scope is stated in its section above: `LocalOK` for local actions, nothing after GOAWAY, and two documented over-approximations of the spec.

## Findings

### H2-01: the connection-level receive window is never enforced

Status: resolved. Fixed in `state.mojo`: `Connection.recv_window` is debited by every DATA payload and credited by every WINDOW_UPDATE(0) (`_conn_window_update`); DATA past it is GOAWAY(FLOW_CONTROL_ERROR). Tests: `test_h2_state.mojo::test_connection_receive_window_is_enforced`, `test_connection_receive_window_is_debited_and_credited`, `test_withheld_connection_credit_restores_the_receive_window`. The Lean model carries the fix as `Fix.shipped`; `Bugs.H2_01.fixed_shipped` is the fix-meets-spec statement and `counterexample` stays about `Fix.none` (the pre-fix code).

- **Severity:** High. Any client can make the server buffer request bodies past both the advertised connection window and the 64 MiB `_MAX_BUFFERED_REQUEST_BYTES` cap, which is the server's only memory bound on buffered bodies. No error is ever raised.
- **RFC:** RFC 9113 §6.9.1: "A receiver MUST treat the receipt of a frame that exceeds the flow-control window as a connection error (Section 5.4.1) of type FLOW_CONTROL_ERROR".
- **What goes wrong:**
  - The DATA branch (`state.mojo:1340-1512`) debits only the stream window.
  - `recv_window` (`state.mojo:446`) is initialised and never read.
  - Above the cap, connection credit is withheld (1492-1511), but a peer that ignores this keeps sending and flare keeps buffering.
- **Counterexample:** `Bugs.H2_01.counterexample`: `¬ ConnWindowOK` on the repro's trace of 4104 DATA frames on 7 streams. `bug` evaluates the end state: peer window -65537, buffered 67239936, withheld 131072, no GOAWAY.
- **Fix:** debit `recv_window` on each DATA frame, raise FLOW_CONTROL_ERROR when a frame exceeds it, and add back every emitted WINDOW_UPDATE(0) (`handleW`). `Bugs.H2_01.fixed` (= `h2_01_fixed`) proves that every trace from a fresh connection then satisfies `ConnWindowOK`.
- **Repro:** `formal/repro/H2-01_conn_window_unenforced.mojo`
- **Observed:** `BUG REPRODUCED: peer overran the connection window to W = -65537 with no FLOW_CONTROL_ERROR; buffered_request_bytes = 67239936 > 64 MiB cap 67108864 after 4104 DATA frames on 7 streams; withheld credit 131072`
- **Flip:** `OK: frame 4100 with W = -1 was answered with frame type 7`, exit 0.

### H2-02: a refused stream id can be reused to open a new request

Status: resolved. Fixed: the server's stream-id check is now `last_peer_stream_id > 0 and sid <= last_peer_stream_id and sid not in streams` (state.mojo), so a refused id is a connection error; the `> 0` guard keeps the stream-0 case with H2-06. Tests: `test_h2_state.mojo::test_a_refused_stream_id_cannot_be_opened_again`, `test_first_stream_id_is_still_accepted`. Model: `Fix.shipped` carries `h2_02` (`idCheck` adds the `0 < lastPeer` guard; `handle_reuse` takes it as a hypothesis); `Bugs.H2_02.fixed_shipped`, `shipped_first_stream`; `counterexample` stays about `Fix.none`.

- **Severity:** Low. A peer can reopen an id the server already refused, which breaks the monotonic-id rule. It gains no capacity, because the limit is still checked for the new request.
- **RFC:** RFC 9113 §5.1.1: new stream ids "MUST be numerically greater than all streams that the initiating endpoint has opened or reserved", and an unexpected id is a connection error of type PROTOCOL_ERROR.
- **What goes wrong:** `state.mojo:1123` rejects `sid < last_peer_stream_id` when the id is not in the table, but not `sid == last_peer_stream_id`. A stream refused with REFUSED_STREAM is never put in the table, so a second HEADERS on the same id opens a new request.
- **Counterexample:** `Bugs.H2_02.counterexample`, with `max_concurrent_streams = 1`:

### H2-05: content-length wraps in Int64, and only the first field counts

Status: resolved. Fixed: `_declared_content_length` parses `1*DIGIT` with an overflow guard, checks every content-length field and returns -2 for a malformed or disagreeing value; `_commit_header_block` resets the stream with RST_STREAM(PROTOCOL_ERROR). Model: the old function is `declaredCLOld`; `Fix.shipped` carries `h2_05`; `Bugs.H2_05.fixed_shipped`.

- **Severity:** Medium. flare's view of the body length can differ from that of an intermediary or application that reads the header itself. This is a request-framing ambiguity of the kind that enables smuggling when the request is forwarded.
- **RFC:**
  - RFC 9110 §8.6: `Content-Length = 1*DIGIT`; differing values must be rejected; and "a recipient MUST anticipate potentially large decimal numerals and prevent parsing errors due to integer conversion overflows".

- **Fix:** parse with an overflow guard, require every content-length field to carry the same value, and otherwise reset the stream with PROTOCOL_ERROR (`declaredCLFixed`). `Bugs.H2_05.fixed` proves `CLSound` for every header list. `fixed_complete` proves that a list whose fields all carry one value n ≤ 2^63-1 yields n.
- **Fix and flip reconciled:** the first flip fixed only the two cases of the repro. The exact Lean fix was then flipped instead:
  - `_declared_content_length` returns -2 on an empty or non-digit value, on overflow (guard `acc > (2^63-1 - d) // 10`), and on duplicates that disagree;
  - `_commit_header_block` answers -2 with RST_STREAM(PROTOCOL_ERROR) and closes the stream.
  - With it, the repro printed `OK: both malformed content-length requests were reset`, and `test_h2_state` (23), `test_h2_server` (10), `test_h2_client_conn` (11) and `test_h2_streaming_state` (10) passed. `flare/` was restored.
- **Repro:** `formal/repro/H2-05_content_length_wrap.mojo`
- **Observed:** `BUG REPRODUCED: 5-byte body accepted as complete with content-length 2^64+5: True ; with content-length 5 and 10: True`
- **Flip:** OK, exit 0.

When the client then opens the stream, every DATA frame of its request is silently dropped (only connection credit comes back), so the request never completes and hangs until a timeout.
- **RFC:** RFC 9113 §5.1, idle: any frame other than HEADERS or PRIORITY is a connection error PROTOCOL_ERROR. §6.4: RST_STREAM "MUST NOT be sent for a stream in the 'idle' state". §5.3.1: a self-dependent PRIORITY is a stream error, which on an idle stream cannot be signalled with RST_STREAM.
- **What goes wrong:** the PRIORITY self-dependency check (`state.mojo:1078-1092`) and the zero-increment WINDOW_UPDATE check (1213-1222) answer with RST_STREAM even when the stream is idle. The later DATA frames hit the `reset_by_us` check (1340-1347).
- **Counterexample:** `Bugs.H2_16.counterexample`: SETTINGS; PRIORITY(1, depends on 1); HEADERS(1); DATA(1, END_STREAM). The replies are `rst 1 1`, nothing, and `wu 0 3`; stream 1 stays open, not half-closed (remote). `bug_wu` shows the WINDOW_UPDATE(1, 0) variant.
- **Fix:** on an idle absent id, both cases are a connection error PROTOCOL_ERROR (`Fix.h2_16`). `Bugs.H2_16.fixed` and `fixed_wu`. Guard `g16` (witness `w16`).
- **Repro:** `formal/repro/H2-16_rst_on_idle_stream_swallows_data.mojo`
- **Observed:** `BUG REPRODUCED: on idle stream 1, PRIORITY(self-dependency) drew RST_STREAM code 1 and WINDOW_UPDATE(0) drew RST_STREAM code 1 ; after HEADERS opened stream 1, DATA("abc", END_STREAM) left state 1 / 1 body bytes 0 / 0 data_complete False / False (OPEN = 1 )`
- **Flip:** `OK: idle-stream PRIORITY/WINDOW_UPDATE drew GOAWAY code 1 / GOAWAY code 1`. `test_h2_state` (23), `test_h2_client_conn` (11), `test_h2_conn_handle` (3) and `test_h2_server` (10) passed.

### H2-17: the client drops PUSH_PROMISE header blocks, so a later response decodes to a wrong header

Status: resolved. Fixed in `client.mojo`: the PUSH_PROMISE special case (RST_STREAM on the promised id, frame dropped) is removed; the frame goes to `handle_frame`, which answers GOAWAY(PROTOCOL_ERROR), so no header block is skipped. Tests: `test_h2_client_conn.mojo::test_push_promise_is_a_connection_error` (the old `test_push_promise_rejected_by_rst_stream`, which encoded the buggy RST_STREAM, is updated and renamed), `test_push_promise_block_cannot_desync_later_responses`. Model: `Fix.shipped` carries `h2_17`; `Bugs.H2_17.fixed_shipped`.

- **Severity:** Medium. flare's HPACK decoder table falls out of step with the server's encoder, and the application receives a header the server never sent. Push is disabled by flare's SETTINGS, but the frame can still arrive: a server may ignore SETTINGS_ENABLE_PUSH, or send it before our SETTINGS is acknowledged. Instead of the required connection error, flare carries on with a corrupted table.
- **RFC:**
  - RFC 9113 §8.4: with push disabled, receipt of PUSH_PROMISE is a connection error of type PROTOCOL_ERROR.
  - §4.3: header compression is stateful, and every field block must be processed to keep the compression state.
- **What goes wrong:** `client.mojo:427-446` intercepts PUSH_PROMISE before `handle_frame`. It answers RST_STREAM(promised id, PROTOCOL_ERROR) and drops the frame, so any insert the server's encoder made in that block is missing from flare's decoder table.
- **Counterexample:** `Bugs.H2_17.counterexample`, with flare's real L1 integer and Huffman codecs and Huffman-coded literals:
  - The response on stream 1 inserts `x-b: 2`, and the PUSH_PROMISE inserts `x-a: 1`.
  - The response on stream 3 sends index 62, which the server means as `x-a: 1`; flare decodes it as `x-b: 2`.
  - No GOAWAY is ever sent. `bug_frame` shows the frame-level reply `rst 2 1`.
- **Fix:** hand PUSH_PROMISE to `handle_frame`, which answers it with GOAWAY(PROTOCOL_ERROR) (`Fix.h2_17`). `Bugs.H2_17.fixed` instantiates `lookup_sound_conn` on the real codec: with the fix, every header list the client returns across the whole connection is the server's. Guard `g17` (witness `w17`).
- **Test to update:** the fix breaks `tests/http2/test_h2_client_conn.mojo::test_push_promise_rejected_by_rst_stream` (about line 465), which asserts RST_STREAM(2, PROTOCOL_ERROR). It should assert that the reply is GOAWAY with error code PROTOCOL_ERROR.
- **Repro:** `formal/repro/H2-17_client_push_promise_hpack_desync.mojo`
- **Observed:** `BUG REPRODUCED: PUSH_PROMISE drew RST_STREAM(2) code 1 instead of GOAWAY(PROTOCOL_ERROR); its field block was not decoded, and stream 3's response (server sent index 62 = x-a: 1) decoded as: x-b: 2;`
- **Flip:** `OK: PUSH_PROMISE drew GOAWAY code 1`. `test_h2_streaming_state` (10), `test_h2_extended_connect` (5), `test_h2_per_stream_cancel` (6) and `test_grpc_client` (3) passed; `test_h2_client_conn` failed only at the test named above.

### H2-18: the client raises on an oversized frame instead of FRAME_SIZE_ERROR

### H2-19: WINDOW_UPDATE is sent on a stream that the DATA frame just closed

- **Severity:** Low. This is the ordinary path of every bodiless client request: HEADERS ends the request, and the response's last DATA frame closes the stream. flare then sends WINDOW_UPDATE on the closed stream. Peers must ignore such a frame for a short while after closing, so the effect is a protocol violation and wasted bytes.
- **RFC:** RFC 9113 §5.1, closed: "An endpoint MUST NOT send frames other than PRIORITY on a closed stream."
- **What goes wrong:** `state.mojo:1492-1494` queues `WINDOW_UPDATE(sid, credit)` for every DATA frame with a payload, after 1470-1478 has already moved a client stream from HALF_CLOSED_LOCAL to CLOSED on END_STREAM.
- **Counterexample:** `Bugs.H2_19.counterexample`: client; SETTINGS; request on stream 1 with END_STREAM; response HEADERS; DATA(1, 3 octets, END_STREAM). Stream 1 is closed and the reply is `[wu 1 3, wu 0 3]`.
- **Fix:** send no stream WINDOW_UPDATE when the frame closes the stream (`Fix.h2_19`). `Bugs.H2_19.fixed`; `fixed_trace` gives `[wu 0 3]`. Guard `g19` (witness `w19`, with `w19_spec`: the spec forbids WINDOW_UPDATE on a closed stream).
- **Repro:** `formal/repro/H2-19_window_update_on_closed_stream.mojo`
- **Observed:** `BUG REPRODUCED: DATA(END_STREAM) closed stream 1 (state 4 = CLOSED) and the reply still carries WINDOW_UPDATE on stream 1 with increment 3`
- **Flip:** `OK: stream CLOSED and no frame sent on it`. `test_h2_client_conn` (11), `test_h2_streaming_state` (10), `test_h2_state` (23), `test_h2_server` (10), `test_h2_conn_handle` (3) and `test_h2_extended_connect` (5) passed.

### H2-20: DATA on a stream the server reset draws PROTOCOL_ERROR, not STREAM_CLOSED

- **Severity:** Low. The connection is torn down either way (a connection error is allowed, §5.4.1), but with the wrong error code, which misleads diagnosis on both sides.
- **RFC:** RFC 9113 §5.1, closed: a frame other than PRIORITY after a RST_STREAM is a stream error of type STREAM_CLOSED. The same holds for DATA on a half-closed (remote) stream.
- **What goes wrong:** the DATA branch (`state.mojo:1340-1512`) tests the client's "headers not complete" condition (PROTOCOL_ERROR) before the stream's state. A stream the server reset before sending response headers therefore takes the PROTOCOL_ERROR path.
- **Counterexample:** `Bugs.H2_20.counterexample`: client; SETTINGS; request on stream 1 with END_STREAM; the server's RST_STREAM(1); DATA(1, 1 octet). The reply is `goaway 0 1`.
- **Fix:** test for a closed or half-closed (remote) stream first (`Fix.h2_20`). `Bugs.H2_20.fixed`; `fixed_trace` gives `goaway 0 5`. Guard `g20` (witness `w20`).
- **Repro:** `formal/repro/H2-20_data_after_rst_wrong_code.mojo`
- **Observed:** `BUG REPRODUCED: DATA on stream 1 after the server's RST_STREAM (state 4 = CLOSED) drew GOAWAY code 1 / RST_STREAM code -1 (expected STREAM_CLOSED = 5; 1 = PROTOCOL_ERROR, -1 = none)`
- **Flip:** `OK: DATA on the reset stream drew STREAM_CLOSED (GOAWAY 5 / RST -1 )`. `test_h2_client_conn` (11), `test_h2_streaming_state` (10), `test_h2_state` (23), `test_h2_server` (10), `test_h2_conn_handle` (3), `test_h2_extended_connect` (5) and `test_h2_per_stream_cancel` (6) passed.

### HPACK-01: lossy UTF-8 conversion desynchronises the dynamic table

Status: resolved. Fixed: `_octets_to_string` (`hpack.mojo:48-76`) stores the octets unchanged (`String(unsafe_from_utf8=b)`), so the dynamic table counts the same octets as the peer. Tests: `test_h2_hpack.mojo::test_invalid_utf8_value_keeps_the_table_in_step_with_the_peer`. Model: the old conversion is `octetsToStringOld`; `octetsToString` is now the identity; `HpackSync.sync_exact_shipped`, `Bugs.HPACK_01.fixed_shipped`, `fixed_real`; `counterexample` and `bug_real` stay about the pre-fix code.

- **Severity:** Medium. A legal header block whose literal values contain non-UTF-8 octets, such as opaque tokens or Latin-1, makes later legal blocks fail with COMPRESSION_ERROR, which kills the connection. `lookup_sound` proves the failure can never be a *wrong* header.
- **RFC:** RFC 7541 §2.3.2 and §4.1: the dynamic table, with sizes counted on octets (name + value + 32), must evolve identically at encoder and decoder. §2.3.3: index 63 is the second dynamic entry.
- **What goes wrong:**
  - `_octets_to_string` (`hpack.mojo:49-63`) stores invalid UTF-8 through `utf8_lossy_string`, which turns each bad byte into U+FFFD (3 octets).
  - The stored entry is therefore larger than the one the peer indexed, so `_evict_to_fit` (290-316) evicts entries the peer still holds.
- **Counterexample:** `Bugs.HPACK_01.counterexample` is a reachable state of the joint LTS:
  - the peer inserts `x-1: a×500`, then `x-2: 0xFF×1300`, so the peer table holds 1870 of 4096 octets;
  - flare stores the 1300-byte value as 3900 octets and evicts `x-1`;
  - index 63 is valid for the peer but out of range for flare.
- **Fix:** store the octets unchanged (`String(unsafe_from_utf8=b)`). `Bugs.HPACK_01.fixed` (= `sync_exact id`): the tables stay identical along every run.
- **Repro:** `formal/repro/HPACK-01_lossy_eviction_drift.mojo`
- **Observed:** `BUG REPRODUCED: index 63 should be x-1 (peer table 1870/4096 bytes) but flare answered GOAWAY code 9 (9 = COMPRESSION_ERROR); stored x-2 value is 3900 bytes, the peer sent 1300`
- **Flip:** `OK: stream 3 decoded x-1 from dynamic index 63; x-2 stored as 1300 bytes`, exit 0.

### HPACK-02: the decode budget never counts the last header

- **Severity:** Low. The budget can be exceeded by exactly one field. That field is still bounded by the frame and header-list caps (`HARD_HEADER_CAP` is 1 MiB), so memory is bounded, but the configured budget is not.
- **RFC:** RFC 7541 §7.3 and RFC 9113 §10.5.1 let a decoder bound how far a header block expands; the budget is that bound, measured in §4.1 sizes.
- **What goes wrong:** `HpackDecoder.decode` (`hpack.mojo:356-441`) charges the *previous* field at the top of each iteration (378-384), so the field decoded last is never charged.
- **Counterexample:** `Bugs.HPACK_02.counterexample`: the single field `a: b×100` (133 octets) decodes without error under a budget of 50.
- **Fix:** charge each field right after it is decoded (`decodeLoopFixed`). `Bugs.HPACK_02.fixed` (= `decode_budget_fixed`); `decode_budget_impl` gives the weaker guarantee the shipped check actually provides.
- **Repro:** `formal/repro/HPACK-02_budget_skips_last_header.mojo`
- **Observed:** `BUG REPRODUCED: a block expanding to 133 bytes decoded 1 header(s) under a budget of 50 with no HPACK_BUDGET_ERROR`
- **Flip:** OK, exit 0.

### HPACK-03: the decoder shrinks its table before the peer can know

Status: resolved. Fixed: `with_config` (server and client) sets only `settings_max_size` and leaves the decoder's `max_size` at 4096 until the peer's size update; the SETTINGS frame advertises `settings_max_size`. Tests: `test_h2_server.mojo::test_reduced_table_size_applies_only_after_the_peers_size_update`, `test_peer_size_update_to_the_advertised_size_is_honoured`, `test_h2_client_conn.mojo::test_reduced_table_size_is_a_ceiling_not_an_immediate_resize`. Model: `fixedInit` is the shipped start state (`shipped_init`, `shipped_size_update`); `counterexample` and `bug_real` stay about the pre-fix `implInit`.

- **Severity:** Medium for servers configured with `header_table_size` below 4096. Every connection from a conforming client that indexes headers before our SETTINGS arrives fails with COMPRESSION_ERROR. The default configuration is not affected.
- **RFC:** RFC 9113 §6.5.3 and RFC 7541 §4.2: a new SETTINGS_HEADER_TABLE_SIZE takes effect only after the encoder receives it, and the encoder signals the change with a size update. Until then the decoder must keep using 4096.
- **What goes wrong:**
  - `Http2Connection.with_config` (`server.mojo:200-203`) sets the decoder's `max_size` to `header_table_size` at construction.
  - With 0, every insert the peer makes under the default 4096 is discarded (`hpack.mojo:299-316`), so the peer's next reference to it is out of range.
- **Counterexample:** `Bugs.HPACK_03.counterexample`: the block `literal-with-indexing x-a: b`, then `indexed 62`, never decodes from flare's initial table. `peer_table` shows the peer's table holds the entry.
- **Fix:** start with `max_size = 4096` and let the peer's first size update lower it (`fixedInit`). `Bugs.HPACK_03.fixed`: for every expanding conversion, the joint invariant holds in every state reachable from the fixed start. `fixed_trace` decodes the block to `[x-a: b, x-a: b]`.
- **Repro:** `formal/repro/HPACK-03_table_size_before_ack.mojo`
- **Observed:** `BUG REPRODUCED: index 62 sent before the SETTINGS ACK should be x-a: b (peer table still 4096) but flare answered GOAWAY code 9 (9 = COMPRESSION_ERROR)`
- **Flip:** OK, exit 0.

HPACK-01, 02 and 03 are also restated on flare's real L1 codec with Huffman-coded literals (`bug_real`, and `fixed_trace_real` for 02 and 03), so the witnesses no longer depend on a toy codec.

## Checked, not a bug

- **Send-window overflow.** WINDOW_UPDATE and SETTINGS_INITIAL_WINDOW_SIZE could in principle push a send window past 2^31-1 without the FLOW_CONTROL_ERROR that §6.9.1 requires. `win_reachable` proves that in every reachable state the connection window lies in [0, 2^31-1] and every stream window is at most 2^31-1, under every fix setting.
- **H2-02 via stream pruning.** The original suspicion was that `_prune_closed_streams` could drop the highest id, allowing it to be reused. Pruning runs only while a new, higher id is being created, so the highest id is never pruned. The only path is the REFUSED_STREAM one described under H2-02.
- **HPACK-01 producing a wrong header.** `prefix_inv` and `lookup_sound` show that for any length-non-decreasing conversion, flare's table is always a converted prefix of the peer's. Any dynamic index flare resolves therefore names the peer's entry; desynchronisation can only show up as COMPRESSION_ERROR. The repro observed COMPRESSION_ERROR.
- **Oversized frames.** `precheck_bounds` and `precheck_refuses` show that no frame longer than `local_max_frame_size` is buffered or dispatched, and `parse_never_raises` shows the frame parser never raises.
- **Wrong headers across a connection.** Apart from H2-17, `lookup_sound_conn` shows that a desynchronised HPACK table can never yield a header the peer did not send, over a whole connection and on the real codec. It can only fail a decode, which is answered with COMPRESSION_ERROR.
- **The client's streaming-body mode.** `ti_run`, `data_credit`, `drain_credit` and `fifo_run` hold for every fix setting, the shipped code included. Credit is never lost or invented, the held-back credit is bounded by one window, and body octets reach the application in order, without duplicates.
- **Out-of-order or oversized dynamic table size updates.** `sizeUpdate_guard` shows they are accepted only at the start of a block and only up to the SETTINGS value.
